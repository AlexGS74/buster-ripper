## 1. CE-1 — does an encoded answer actually reach this proxy?

### 1a. The proxy asks for one, on both arms (settles dimension 5 live, not by claim only)

Production proxy (`python -m buster_ripper.main --upstream http://127.0.0.1:39631`) against
a raw-socket echo listener that prints the head it receives.

Arm 1 — downstream client names **no** `Accept-Encoding` (`GET /v1/models HTTP/1.1` with only
`Host:` and `Connection: close`):

```text
GET /v1/models HTTP/1.1
Host: 127.0.0.1:39631
Accept: */*
Accept-Encoding: gzip, deflate          <-- aiohttp's own default (claim 389), on the wire
User-Agent: Python/3.13 aiohttp/3.13.3
```

Arm 2 — downstream client sends `Accept-Encoding: gzip, deflate, br`:

```text
GET /v1/models HTTP/1.1
Host: 127.0.0.1:39631
User-Agent: Python-urllib/3.13
Accept-Encoding: gzip, deflate, br      <-- forwarded unchanged by forward_headers
```

`buster_ripper/utils.py:23` — the `forward_headers` drop list is
`("host", "content-length", connection, transfer-encoding, + _HOP_BY_HOP)`; `accept-encoding`
is not in it. Both arms therefore put an encoding request in front of the upstream, exactly as
the composition traced.

### 1b. The proxy's client never turns decompression off

```text
$ grep -rn "auto_decompress\|skip_auto_headers" buster_ripper/     -> zero matches
```

`buster_ripper/server.py:65-68` — the package's only `ClientSession` names `timeout=` and
`connector=` only. Claims 384/385 resolve this to `auto_decompress=True` at every request site.

`http://hyperipper.local:30001` — the endpoint `tests/qa/harness.py:39` declares as `UPSTREAM`
and the one the `QAP-MS001` (10/10) and `QAP-MS002` (15/15) live gates ran against; `mDNS` →
`192.168.50.132`; `/v1/models` reports `owned_by: "vllm"`, root

| Request | Offered `Accept-Encoding` | `Content-Encoding` in answer |
|---|---|---|
| `GET /v1/models` (488 B JSON) | `identity` | none |
| `GET /v1/models` | `gzip, deflate` | none |
| `GET /v1/models` | `gzip, deflate, br, zstd` | none |
| `GET /metrics` (**66 535 B `text/plain`** — a prime compress candidate) | `identity` / `gzip, deflate` / `gzip, deflate, br, zstd` | none, all three |
| `POST /v1/chat/completions` (`max_tokens=1`) | `gzip, deflate, br, zstd` | none |

`server: uvicorn` is the terminal `Server` value on every answer — no nginx/traeefik/Caddy

## 2. CE-2 — is the duplicate-name fold base parity?

**It is not.** The claim on `quality-backlog.md` ("Both are base parity") is refuted for CE-2 and
stands for CE-1. The two clients' `.items()` semantics differ, and that difference decides it.

### 2a. The deployed upstream repeats header names — on every response, with differing values

Raw socket, no proxy, no fixture:

```text
$ printf 'GET /v1/models HTTP/1.1\r\nHost: …\r\nAccept-Encoding: gzip, deflate, br, zstd\r\n\r\n'
HTTP/1.1 200 OK
  1: date:   Tue, 06 Oct 2026 19:32:07 GMT
  2: server: uvicorn
  3: date:   Tue, 06 Oct 2026 19:32:07 GMT     <-- second occurrence of the same name
  4: server: uvicorn                            <-- second occurrence
  5: content-length: 488
  6: content-type: application/json
  7: connection: close
name occurrence counts: {'date': 2, 'server': 2, 'content-length': 1, 'content-type': 1, 'connection': 1}
```

An earlier sample of the same endpoint carried **two different** values in one response
(`date: … 19:10:53 GMT` and `date: … 19:10:54 GMT`). Measured deliberately, 6 consecutive
`GET /v1/models` requests, counting occurrences and distinct values per response:

```text
sample 1: date occurrences=2 server occurrences=2 -> same
sample 2: date occurrences=2 server occurrences=2 -> same
sample 3: date occurrences=2 server occurrences=2 -> DIFFER   ('…19:42:12', '…19:42:13')
sample 4: date occurrences=2 server occurrences=2 -> same
sample 5: date occurrences=2 server occurrences=2 -> same
sample 6: date occurrences=2 server occurrences=2 -> same

1/6 responses carried two DIFFERENT date values; 5/6 carried identical ones
6/6 responses carried two date occurrences and two server occurrences
```

So the fold discards an occurrence on **every** response, and discards a *distinct* value
roughly one response in six — whichever `Date` the second hop stamped. The kept value is the
**last** occurrence, so the timestamp a client sees is whichever hop happened to be added
last, not the origin's.

### 2b. The consumer folds them, live, through `buster_ripper.utils.response_headers`

```text
producer (aiohttp CIMultiDictProxy) .items(): 6 occurrences
    ('Date', '…19:32:07 GMT')  ('Server', 'uvicorn')  ('Date', '…19:32:07 GMT')
    ('Server', 'uvicorn')      ('Content-Length', '488')  ('Content-Type', 'application/json')
consumer response_headers(): 3 entries ->
    {'Date': '…19:32:07 GMT', 'Server': 'uvicorn', 'Content-Type': 'application/json'}
occurrences dropped: 3
```

And end-to-end through the running production proxy against the same live upstream:

```text
downstream head: Date x1, Server x1          (upstream sent Date x2, Server x2)
```

### 2c. The same input through the base's client keeps the values

Both expressions are copied verbatim from their sources — `buster_ripper_legacy.py:630-637`
(`_response_headers`) and `buster_ripper/utils.py:36-40` (`response_headers`) — applied to the
same header head (two `date`, two `server`, two `set-cookie`, one `content-encoding`):

```text
BASE expression over httpx 0.28.1's .items():
   {'date': 'T1, T2', 'server': 'uvicorn, uvicorn', 'set-cookie': 'a=1, b=2', 'content-encoding': 'gzip'}
   -> every occurrence's VALUE reaches the client, comma-joined into one field-line

BRANCH expression over aiohttp's per-occurrence .items():
   {'date': 'T2', 'server': 'uvicorn', 'set-cookie': 'b=2', 'content-encoding': 'gzip'}
   -> all but the last occurrence's value is destroyed
```

Source of the difference (read this pass from an installed httpx, `_models.py`):

```python
def items(self) -> typing.ItemsView[str, str]:
    """Return `(key, value)` items of headers. Concatenate headers
    into a single comma separated value when a key occurs multiple times."""
```

`multi_items()` is the same class's own per-occurrence alternative — its existence is the proof
that `items()` merges. httpx's default request headers advertise `Accept-Encoding` too
(`_client.py:120,310`, value `gzip, deflate`), and `httpx.Response.read()` is
`self._content = b"".join(self.iter_bytes())` over "the decoded response content" — so the base
had CE-1's mismatch in full and CE-2's loss not at all.

**Asymmetry worth recording:** the base's *request* filter (`_forward_headers`,
`legacy.py:621-627`) iterated Starlette `Request.headers.items()`, which yields
per-occurrence pairs (`starlette/datastructures.py:534-535`), so the base's dict comprehension
folded last-wins on egress exactly as `forward_headers` does today. The composer's Note N2
(egress has the same fold) is therefore correct *and* base parity — only the response direction
diverged.

### 2d. Reach verdict

**`reached`.** Cited path: the operator-declared upstream (network input) →
`passthrough.py:38/41` / `messages.py:270/291` / `chat.py:149,165,217,221` →
`utils.py:36-40` → `web.Response(headers=…)` → the client. Observed on a live proxied request in
§2b, not in a fixture.

## 3. Feasibility of the selected CE-2 closure (per-occurrence preservation)

Not an implementation — a check that the closure the gate selected is real, so the routing is
not handed an unimplementable requirement.

```text
dict (today's shape)        : n=3 items=[('Date','T2'),('Server','uvicorn'),('Set-Cookie','b=2')]
CIMultiDict(pairs)          : n=5 items=[('Date','T1'),('Server','uvicorn'),('Date','T2'),
                                         ('Set-Cookie','a=1'),('Set-Cookie','b=2')]
list of pairs               : n=5   (identical)
CIMultiDict == dict         : True          -> existing dict-comparison witnesses keep passing
'date' in CIMultiDict       : True          -> case-insensitive membership preserved
```

`web.Response(headers=…)` accepts both a `CIMultiDict` and an iterable of pairs, and the D-section
relay above shows the wire emitting one line per occurrence when the head carries them. The only
existing witness the change can trip is `tests/test_header_parity.py:261-263`
(`source.count("for k, v in") == 2` in `utils.py`), which a comprehension-shaped
`CIMultiDict((k, v) for k, v in …)` keeps satisfied — recorded in T017's done-when.

## 4. What this pass did NOT establish

- No claim about what a *different* deployment (a gateway with `gzip_types application/json`)
  would answer. §1c is about the upstream this tree declares and reaches today.
- No posture ruling on CE-1. Its remedy is a parity deviation with three materially different
  shapes (drop `content-encoding` at the filter / force `identity` on egress / relay wire bytes);
  the composition's Note N3 says nothing in its six members is normative about that, and no
  session authority ranks them. It routes to `roadmap.md` §RM-008 and gates nothing.
- No base-pinned wire shape for CE-2's repeated names: base's exact httpx pin is not recoverable
  in-tree (httpx is no longer a dependency; `pyproject.toml` declares `aiohttp` + `click`;
  `uv.lock` names no httpx). The merge behavior was read from an installed 0.28.1 and does not
  depend on the pin for the conclusion — under *any* base `items()` semantics the base never
  dropped an occurrence's value, while the branch does.
- Whether S1–S14's terminal rows are affected. They are not: this pass moved no cell of any row
  outside 384–389 and the `S15` row.
