# T017 — the RUNNING production proxy, same measurement at the base bytes and at the fixed bytes

Captured 2026-10-06 by the `075-01-forward` pass. Driver: a throwaway script kept **outside the
repository** (`…/t017/demo_relay.py`, run as `.venv/bin/python`), which starts
`python -m buster_ripper.main --upstream <target> --host 127.0.0.1 --port <free>` exactly as
`serve_buster_ripper.sh` does, then speaks raw HTTP/1.1 to it over a socket and prints the bytes
that came back. It writes nothing under `buster_ripper/` or `tests/`, and neither run was piped
through the test suite — this is the served path, not a fixture assertion.

  `git stash push -- buster_ripper/utils.py`, the only file of the whole tree that differs.

  plus `Connection` twice to exercise the drop over occurrences.

## Reading

**Section 1 — the fold, shown on one head.** The fixture sends `X-Repeat: first` and
`X-Repeat: second`; at the base bytes the relayed head carries **`X-Repeat: second` alone** —
`first` is not in those bytes at all, and the same for `Set-Cookie: a=1` and the earlier
`Date`. Counters 1/1/1. At the fixed bytes the head carries both, **in the order the upstream sent
them**, and the counters read 2/2/2. The two `Connection` lines are gone in **both** runs: the
single `Connection: close` in each relayed head is aiohttp's own server answer to the client's
`Connection: close`, not a relayed occurrence — compare the upstream block directly above it, where
`Connection: one` and `Connection: two` sit between the cookies. So the drop census still holds over
*occurrences*, not merely over names, and `Content-Length: 2` is still re-derived from the body that
was actually sent rather than relayed.

**Section 2 — the same measurement the routing pass made, re-run on the fixed bytes.**
`evidence/s15-reach-and-base-comparison.txt` §2b recorded, at the base bytes, `downstream head:
Date x1, Server x1` against `date` ×2 / `server` ×2 from the upstream. That counter is reproduced
here verbatim in the BASE run (1/1). In the FIXED run it is **2/2**, on a response whose two `date`
values happened to differ by a second (the 1-in-6 case §2a measured), so the value that used to be
destroyed on this deployment is a real, different timestamp rather than a cosmetic duplicate — and
the live upstream is still repeating both names on every answer.

**What this adds over the suite.** `tests/test_header_parity.py` proves the same property on
`StubUpstream` through `conftest.py`'s fixtures; this proves it on the module's only production
consumer, with the real connector, the real `ClientSession`, the real `web.Response` writer and the
real operator upstream in the loop. It is the demonstration the plan's `Reach: reached` verdict was
built on, run a second time against a tree that no longer has the defect.
