## Composition

Producer → transformations → consumer, as the 19 resolved members jointly allow it:

**Producer.** `_stream_single_request` (`messages.py:121-181`) runs its whole body inside one `try` opened at 129 whose only handler is 179 (241). The relay loop at 156-174 then pushes upstream bytes unchanged (67); the success terminal is `write_eof()` + `return response` at 176-177.

**Transformation 1 — the caught channel (179 → 181).** What can raise here is decided by class hierarchy alone, and rows 330/331 settle it in both directions. Payload errors are inside (`ClientPayloadError` is a direct `ClientError` child — 231); the client-disconnect signal raised out of `write()` is inside (`ClientConnectionResetError` → `ClientConnectionError` → `ClientError`, per 233's class chain); the three named timeout classes are inside (330). Outside the arm: the bare `asyncio.TimeoutError` that `TimerContext.__exit__` substitutes for the expired cumulative `total` budget (331), and the `AttributeError` from the unguarded `.get()` chain at 161-165 (245 + 239 + 240 + 244). 242 confirms there is no second arm, no tuple, no `except Exception`, no nested `try`. The committed `StreamResponse`, which is the only object holding the fact that a head already went out, is discarded at 181 rather than consulted; `prepare()`'s re-entry guard is per-object state (227), so it cannot protect the connection.

**Transformation 2 — the raise-out channel.** Nothing between 179 and the server catches the outside set: `handle_streaming` (73-118) has no `try`, and `handle_messages`' only `try` (26-28) wraps `await request.json()`. So a post-commit outside-set exception reaches the server with the head already committed.

**Consumer.** Both channels arrive at the same place, and what aiohttp does there differs. For a *returned* response, `finish_response()` runs `await prepare_meth(request)` then `await resp.write_eof()` (230). 229: `prepare()` on a second, distinct response for a request whose first head is committed re-binds the request's original `StreamWriter` (`web_request.py:169` never clears it), `write_headers()` resets `_headers_written = False` and replaces `_headers_buf` with the new status line + headers, and `finish_response()`'s `write_eof()` flushes it — two committed responses on one connection, no error raised anywhere. A `Response` (which is what `json_response` builds — 228) buffers rather than flushing at prepare, so its head lands on that following `write_eof()`. For a *raised* exception, 230: `_handle_request` routes `except asyncio.TimeoutError` → `handle_error(request, 504)` and `except Exception` → `handle_error(request, 500, exc)`, and `handle_error()` refuses when `request.writer.output_size > 0` by raising `ConnectionError("Response is sent already, cannot send another response with the error message")`, caught in `start()` as "Ignored premature client disconnection" → `break`: the error turn is dropped and the connection closed. `CancelledError` is re-raised before any response (230, with 78 establishing it is outside `Exception`, so the module's own arm cannot catch it either).

Net: the head crosses once (154), and after that crossing the handler has two exits that the caller cannot tell apart — one that makes the server write a **second** head onto the live connection, and one that makes the server **refuse to write any** head and close the turn.

## Counterexample

Three concrete orders, plus one named-unclear item. All of them use only a healthy downstream connection and a normal Anthropic-shaped streaming response.

**CE-1 — one accepted request, two committed heads (D1, D3, D4).**
Order: `POST /v1/messages` with `"stream": true` → `handle_messages:67-68` → `handle_streaming`; `backend.get_backend_state()` is not `"sglang"`, so 84-85 is a single dispatch. `session.post` (130) returns **200**, so 136 is false. 145-153 build the `StreamResponse`; **154 commits** `HTTP/1.1 200 OK` + the fixed SSE header block and flushes it (226). The first chunk arrives and is written verbatim at 174 (67). Upstream then ends the message prematurely — the peer closes before the payload completes — and `async for … resp.content.iter_any()` at 156 raises `aiohttp.ClientPayloadError`, which is a `ClientError` (231), caught by the sole arm at 179 (241, 242). The arm returns a **new** `web.json_response(…, status=502)` (243), unprepared and writer-less (228); `handle_streaming:85` → `handle_messages:68` hand it up unchanged; `finish_response()` prepares it (230); and because the re-prepare guard is per response *object* (227) while the writer is per *request* and never cleared (229), the connection now also carries `HTTP/1.1 502 Bad Gateway` + a JSON header block, flushed by `finish_response()`'s `write_eof()`, positioned inside the body stream of the 200 response that 176 never terminated.
Observable result: the client's only parseable status is `200`; the intended 502 and its `{"error": …}` body arrive as bytes in the middle of an event stream, where no conforming HTTP client reads them as a status, and the response never terminates. The same arm, reached from line 130 instead of 156 (a connect-level `ServerTimeoutError` — a `ClientError` per 330, so caught identically), produces exactly one head and a correct 502. Nothing at 179-181 distinguishes the two, and the one object that *does* record the distinction is thrown away at 181.
Scope honesty: 229's swallow corner (a buffered `Response` head is lost if the writer is already at `_eof`) does not apply here — 176 is not reached, and no member identifies another path that sets `_eof` on the request writer while the downstream transport is healthy. If the downstream transport were closing, `send_headers()`' `_write` would raise instead (233), which is D8's case below.

**CE-2 — a telemetry-only fault leaves the request unsettled (D5, D7).**
Order: same arrival and commit as CE-1. Upstream sends `data: {"type":"message_start","message":"x"}`. `find_message_start` (158) checks nothing but `type` and returns the decoded dict unchanged (244); `json.loads` gives a plain Python `str` for that nested string value (240); 161-165 then call `.get("usage", {})` on it with no type narrowing anywhere in the function (245); `str` has no `get` attribute (239), so **`AttributeError`** fires at 163 — before 174, so the chunk that triggered it is never even relayed. `AttributeError` is not a `ClientError`, so nothing catches it (242) and it exits `_stream_single_request`, `handle_streaming` and `handle_messages` untouched. The server takes `except Exception` → `handle_error(request, 500, exc)`, whose `output_size > 0` guard is satisfied by the 154 commit, so it raises `ConnectionError("Response is sent already…")` and the turn is dropped with the connection closed (230).
Observable result: no 502, no 500, no body — a truncated event stream and a closed connection, with a server-side traceback as the only witness. A payload value that exists purely to populate `capture["input_tokens"]` and one log line therefore aborts a committed client response.

**CE-3 — one timeout configuration, two opposite terminals (D2).**
Order: identical in both branches up to the commit at 154; the fault is the same event, "the upstream stalled and aiohttp gave up on it", raised from the same `async for` line inside the same `try` (241).
- Branch a: the `sock_read` budget expires → `SocketTimeoutError`, a `ClientError` (330) → caught at 179 → CE-1's route → a second header block is written onto the client's live stream.
- Branch b: the cumulative `total` budget expires → `TimerContext.__exit__` raises bare `asyncio.TimeoutError` (331), not a `ClientError` → uncaught (242) → CE-2's route → the turn is dropped and the connection closed with nothing.
`ServerTimeoutError` sits in *both* sets (330: it inherits `ClientError`'s chain *and* `asyncio.TimeoutError`), and `client.py`'s pass-through guard for the bare `TimeoutError` (331) shows the non-membership is deliberate library behavior, not an accident of this version. So the discriminator between "client gets a corrupted double head" and "client gets a silent truncation" is a class-hierarchy fact that no line of this handler mentions or could see.

**Witness (D9).** None of CE-1, CE-2 or CE-3 is exercised anywhere in the suite: no test names `_stream_single_request`, and none calls or patches `prepare()` or any preparation collaborator; the failures the suite injects sit at the `session.post`/`session.get` stub boundary, which is pre-commit by construction (248). The post-commit half of this seam has no gate on either side of the boundary.

**Named-unclear item (D8) — missing contract.** A downstream client disconnect is detected as `ClientConnectionResetError` from `write()` at 174 (233), which is `ClientError`-derived and therefore enters the arm whose log text is `"Upstream error: %s"` and whose return is a 502 "upstream failed" document (243). The composed facts are that a client leaving is reported, and answered, as an upstream failure; whether any of that answer reaches a wire (229's swallow corner turns on writer `_eof`, which 233's detection-timing caveat leaves open for a just-FIN'd peer) and whether downstream loss is *allowed* to be surfaced as an upstream error are both unanswered by every member supplied. This is not counted as a counterexample; the missing contract is a statement of whose disconnect semantics own the arm at `messages.py:179`.
