## Counterexample

### CE-1 — two distinct `source` mappings receive one identity inside one forwarded request (and one of them is destroyed)

Exact input. `STRIP_IMAGES` on (`--strip-images`, `main.py:74`; default false at `config.py:40`), `IMAGE_CACHE_MAX_SIZE` at its default 100 (`config.py:41`). One client conversation, one `sid` (stable because `normalize.py:50-61` strips the per-request billing nonce before `session_id` runs — `messages.py:34-35`). By turn 14 of a conversation that adds one image per turn, the map is at the cap: turn *k* strips *k* image blocks (all resent history, `image.py:128-136`), so the entry count is 1, 3, 6, …, 91 after turns 1–13 and reaches 100 mid-turn-14.

Now take the same turn-14 request shape the suite itself exercises — a single user message with two image blocks and distinct sources (`tests/test_image.py:86`, `:88`, one `strip_and_cache_images` call at `:93`; row 339), with the session map already at `len == 100`:

1. Block A (`source` = `{"url":"data:image/png;base64,A…","type":"base64"}`): `image_key = f"img_{len(…)}"` = `img_100` (`image.py:81`); write → 101 entries (`:84`); `_evict_by_lru` deletes the single oldest → 100 entries (`:68-75`).
2. Block B (`source` = `{"url":"data:image/jpeg;base64,B…","type":"base64"}`): `len(_image_cache[sid])` is 100 again — per 309 the eviction restored the count and, had the key already existed, an overwrite would not have grown it either — so `image_key` = `img_100` **again**; `_image_cache[sid]["img_100"] = (B, ts)` replaces A's entry (`image.py:84`, 333); `_evict_by_lru` returns at `:68` since 100 ≤ 100.
3. Both blocks become `{"type":"text","text":"[image:img_100]"}` (`image.py:90-93`, 274).

Observable result. The body forwarded to upstream (`messages.py:130-134` / `:231-235`) and written by `dump_turn` (`:55-57`) describes two different client images with **one byte-identical token**, and A's `source` mapping is now referenced by nothing in the body (`image.py:136` replaced that content list; 277) while the cache slot that A's placeholder names holds **B**. Nothing that resolves `[image:img_100]` can recover A, and the module's own contract for this value — `image.py:111-112`, "Replaces image blocks with placeholder references that can be restored later" — is unsatisfiable for A. With three blocks in one message, all three collapse to `img_100`. With the map at the cap, **every** image block in **every** later request of that namespace is named `[image:img_100]`.

Path through verified claims: 272 (count read before insert; non-monotonic under `_evict_by_lru`, "a later key can repeat an earlier one and overwrite that entry") → 309 (same-key assignment does not change `len`) → 333 (element 0 is that block's own `source`) → 274 (the placeholder text **is** the key) → 277 (the replaced body no longer holds the dropped mapping).

### CE-2 — the same `source` mapping receives a different identity across requests, and equal mappings receive different bytes

**(a) Positional drift for identical content.** Fresh namespace, turn 1: one image A → `img_0`; forwarded text `[image:img_0]`. Turn 2 (A resent in history plus a new image B): `strip_and_cache_images` walks **all** user messages in order (`image.py:128-136`), `len` is now 1, so A is re-keyed `img_1` and B `img_2`; forwarded text `[image:img_1]` for the block that was `[image:img_0]` one turn earlier. Same client, same image, same conversation position, different text — while 284/286 keep the namespace (`sid`) fixed. Because the prefix cache keys on exactly that text (T6.2; `normalize.py:1` and `messages.py:31-33` state the purpose), the identity chain the seam describes is unstable in the one direction the module exists to stabilize. Conversely, per CE-1, *different* content shares one text. Both directions follow from the key being a counter rather than a digest — 272/274 versus 286.

**(b) No canonical serialization anywhere.** `source` is never passed to `json.dumps` (T4: zero `sort_keys`/`separators` sites in `buster_ripper/`). When T3's gate is false — `STRIP_IMAGES` off, or the last user message carrying no image (`image.py:35-42`, `break` after the first user message seen from the end) — the mapping is forwarded verbatim, so two clients sending equal `source` mappings with different insertion order get different bytes upstream, which is precisely what 279/280/281 would have prevented had production enabled the option. The `lang:python` half of this seam is verified but unreferenced.

### CE-3 — the namespace is shared, and the payload outlives every reclaim path

Fresh `buster_ripper` bytes, `rg -u "clear_session_cache|cleanup_expired_images\(|get_cached_image" buster_ripper -g '*.py'` returns only the three definitions at `image.py:141`, `:176`, `:182`; with 287 (no caller for `get_cached_image`) the read side, the TTL side (`_cleanup_expired_images` is called only from `image.py:155` and `:179`) and the clear side (`image.py:182-185`, 347) are all unreachable in production.

Two ordered events. (i) Client X posts a request with no `system` field: `session.py:95` defaults to `""`, so `sid` is the fixed 12-char digest of the empty string (284: identical bytes → identical digest; 286: nothing else contributes). (ii) Client Y posts a different conversation, also with no `system` field: same `sid` → **the same `_image_cache[sid]` map and the same counter** (272, 333). Their interleaved image blocks take turns incrementing that one count, so X's placeholder and Y's placeholder can name the same slot; once that namespace hits the cap, CE-1 applies across the two clients, and the entry `X`'s text names holds `Y`'s base64 mapping. Separately, per 277 each such entry keeps the caller's own parsed mapping alive with no age-based reclaim reachable and no cap on the number of `sid` keys (`image.py:121-122` only ever adds), so `buster_ripper.image._image_cache` grows one namespace per distinct 12-char digest for the process lifetime.

This is a composition fact, not a claim that restoration is intended today: the reason CE-1's lost image is *not* visible as a wrong-image response today is precisely that no production code reads the cache (287). The identity chain has a writer and no reader.

### CE-4 — supporting: which `source` mappings get an identity at all is decided by a different message (no member row covers the gate)

`image.py:25-44` (`has_images`) inspects only the last user message and `break`s; `image.py:128-136` (`strip_and_cache_images`) rewrites **every** user message. Ordered input, `STRIP_IMAGES` on: `messages = [user([image A]), assistant("ok"), user("thanks")]` → `has_images` false at `messages.py:38` → A is forwarded as a full base64 image block, no key, no cache entry. Same conversation with `"thanks"` replaced by a new image block → `has_images` true → A is replaced by `[image:img_N]` and its base64 is removed from the forwarded body. The same `source` mapping at the same position in the same conversation flips between full base64 payload and a 13-character token (changing what the upstream prefix caches and what `session.py:90`'s `estimate_tokens` reports) on the strength of a later message. Exactness caveat, recorded because the protocol requires the path to run through verified claims: 272/274/277/333 establish what happens once the strip runs, and 266/267 establish the strip's position, but **no S13 member row asserts anything about `has_images`' last-user-message gate** — that step rests on the cited production source alone, so this item is supporting rather than an independent finding.

### Contract gaps (why these are not separate findings)

Whether `[image:img_N]` is contractually a *restorable* reference, a *stable* prefix token, or only a human-readable marker is not established by any production contract beyond the docstring sentence at `image.py:111-112` and the module purpose at `normalize.py:1`. If the intention is "marker only, never resolved" (consistent with 287), then CE-1's destroyed mapping is still a defect (the request body stops distinguishing two client images) but CE-3's cross-tenant slot naming is latent. Naming that intention is a Decide-side act, not a composition result, so it is recorded as a missing contract rather than resolved here.
