## Counterexample

Four of these are live on the shipped code today; the fifth is conditional on the sweep becoming reachable.

**CE-1 — a client-supplied `messages` shape that survives every other guard is answered with aiohttp's generated 500 and a forced connection close.** With `--strip-images` on (`config.STRIP_IMAGES` default False, `main.py:44`), request `POST /v1/messages` body `{"system": "s", "messages": {"x": 1}}`: `request.json()` succeeds; `normalize(body, session_id="")` succeeds — every message walk in it is behind an `isinstance(..., list)` test (`normalize.py:133,187`); `session_id(body)` succeeds; then the route's guard calls `image_handler.has_images(body)` at `messages.py:38`, which does `for msg in reversed(messages)` on a `dict` (`image.py:35`) and raises. (For `{"messages": "hi"}` the same line accepts `reversed()` and `msg.get("role")` raises on the character — either arm, an `Exception`.) No `try` in `handle_messages` covers that line (263), `logging_middleware` does not catch (314), it is the only middleware (315), and nothing has been committed, so `_handle_request`'s `except Exception` produces `handle_error(request, 500, exc)` → `500 Internal Server Error`, `text/plain` (or the HTML variant when `Accept` contains `text/html`), `force_close()` (230). Observable: with the flag off the same body is proxied to upstream and gets upstream's 4xx; with the flag on the proxy answers a client-shape error as a server error and drops the keep-alive connection — while the sibling fault path in the same handler (`dump_turn` at `:56-59`) is caught, logged and tolerated. The exception class name is this pass's reading of `reversed()`/`str.get`; the transport outcome does not depend on which it is.

**CE-2 — `--image-cache-ttl` bounds nothing reachable.** The TTL value is read at exactly one site, `_cleanup_expired_images`'s `now - ts > config.IMAGE_CACHE_TTL` (`image.py:56`, 296/298; 298's full-file scan confirms no other occurrence in the module). Its only two callers are `get_cached_image:155` — which has no caller anywhere under `buster_ripper/` — and `cleanup_expired_images:179` — which has no caller under `buster_ripper/` or `tests/` (300). So no request path can ever evaluate the comparator, and `main.py:127`'s advertised "Image cache TTL in seconds" changes nothing an operator can observe (48). Retention is bounded only by the per-session count (302/305). Consequence pair: an entry whose age exceeds the TTL by hours stays cached and resolvable indefinitely; and dimension 4's strict-vs-inclusive boundary has no observable consequence today for the same reason.

**CE-3 — nothing in production owns the emptied-session-dict drop, and the outer mapping grows monotonically on client input.** Per 11 the outer key is `sha256(system)[:12]`; per 259/`:121-122` a writer call creates it; per 295 and 305 no sweep or eviction ever removes it; per 299 the global janitor — which is the primitive that would at least visit every session — performs no drop and is caller-less (300); per 301 the one primitive that does drop it has no production caller; per 306 the mapping is never rebound and there is no other re-initialiser (`_image_cache.clear()` appears only in the test fixture, 294). Observable: N distinct `system` strings that each send one image leave N permanent outer entries and N permanent inner entries — neither bound (count per session, time) can remove them on any reachable path.

**CE-4 — the stamp used as the recency ordering is a reversible wall clock, so one clock step pins the real-time-oldest entry against the only live bound.** Members 302 and 303 make `_evict_by_lru` order deletions by ascending stamp and delete `len(cache) - MAX_SIZE` of them; 311 establishes the stamp's clock "can return a lower value than a previous call if the system clock has been set back". Exact ordering: `IMAGE_CACHE_MAX_SIZE = 2` (or any value), entry X inserted at wall `t = 1000`, the system clock then steps back 600 s, entries Y and Z inserted at `400` and `401`. The next insert over the limit sorts `[Y(400), Z(401), X(1000)]` and deletes **Y** — an entry younger than the survivor. X holds the largest stamp, so it is last in every subsequent deletion slice until wall time passes 1000 again, and its TTL age (`now - 1000`) is negative, so when CE-2's reachability is fixed the strict comparator (297) still cannot expire it. Observable against the function's own stated rule ("Sort by timestamp and remove oldest entries", `image.py:71`; the suite's "First image should be evicted (oldest)", `tests/test_image.py:195`) and, once a sweep is reachable, against the advertised TTL: a clock adjustment converts the entry stamped immediately before it into the most-pinned entry in that session, immune to both bounds. The reverse step direction is equally concrete: a forward jump of more than the TTL makes every cached entry expired at the next sweep, so live sources are dropped while their placeholders remain in the conversation.

**CE-5 — the size-derived key and post-insert eviction collapse distinct images onto one identity and then freeze both bounds; this is reachable at default configuration.** Members 275 (evict runs *after* the insert), 302 (early return once `len(cache) <= MAX_SIZE`) and 276 (a write under an existing key replaces the entry wholesale, and a recomputed index "can name a live key") compose into a stable stuck state. Exact input at defaults (`IMAGE_CACHE_MAX_SIZE = 100`, `main.py:125`; `--strip-images` on), one `sid` (one system prompt, 11; 306 shares the row process-wide): requests #1…#100 fill `img_0 … img_99` without evicting (275 evaluates against the post-insert size, 302 returns at `100 <= 100`). Request #101 derives `img_100`, inserts, `len == 101 > 100`, so `_evict_by_lru` deletes the single oldest — `img_0` — leaving `img_1 … img_100` at count 100. Request #102 derives `img_{len}` = `img_100`, which is a **live key**: 276's plain `dict.__setitem__` replaces it, the count stays 100, and from then on `len(cache) <= MAX_SIZE` holds forever, so 302's early return means **nothing is ever evicted again**. Observable results of one accepted composition: (i) every image from #102 onward is forwarded as the byte-identical placeholder `[image:img_100]` — two different images, one identity, in the body sent upstream, and turns that named `img_100` earlier now denote the newest bytes; (ii) the replacement carries a fresh stamp, so it is newest under 303's ordering and un-aged under 296/297's comparator — a steady stream of one-image requests keeps `img_100` alive indefinitely even after CE-2 is fixed; (iii) `img_1 … img_99` are pinned by the same stuck count and, with the sweep unreachable (CE-2), are never reclaimed by time either. Multi-turn conversations reach it in tens of requests rather than hundreds, because the writer reprocesses *every* user message (`image.py:128-136`) on each call while the route's detector inspects only the last user message (`image.py:35-42`), so already-cached images are re-inserted under new count-derived keys every turn — which also means one image's placeholder text differs from request to request.

**Conditional (dimensions 1, 2, 7, 4):** once a sweep is called from inside the writer, the same members make it request-path-visible in three specific ways — a head-window sweep changes the `img_N` identities of the call that follows it (276 + `:81`) where a tail sweep does not; an every-session sweep (299) makes a session's key identities depend on foreign sessions' expiry timing (305 is the only scope that does not); and a 3-tuple entry makes `:55` and `:160` raise `ValueError` (296/308 + 310) from inside the request, which 263/314/315/230 transport as a 500, while `:72` keeps working silently. Also `--image-cache-ttl 0` (the option has no minimum, `main.py:127`) makes a tail sweep delete the entries inserted earlier in the same call, since the sweep re-reads `now` at `:53` after the stamps were written — leaving a body whose placeholders resolve to nothing; and at exactly `age == TTL` the strict comparator (297) keeps the entry, with no witness either way (293). Deciding which of these the design should accept is outside this role.
