## Claim

Iterating `aiohttp.web.Request.headers.items()` yields each header name spelled as the client sent it

## What it actually does

With the default C/Cython parser (the one aiohttp installs and uses unless built with `AIOHTTP_NO_EXTENSIONS=1`), a received header name that matches a **known** header case-insensitively is replaced by aiohttp's own canonical spelling from `aiohttp/hdrs.py`, so `items()` yields `Content-Type` for a client that sent `content-type`, `CONTENT-TYPE` or `cOnTeNt-tYpE`, and `Etag` for a client that sent `ETag`. Only names absent from that table (custom `X-…` headers, anything not in `hdrs.py`) come back spelled as the client sent them. `web.Request.raw_headers` is the accessor that is verbatim (`(bytes, bytes)` as received).

The pure-Python fallback does behave as claimed — `HeadersParser.parse_headers` stores `name = bname.decode("utf-8", "surrogateescape")` into the `CIMultiDict` without touching case (`aiohttp/http_parser.py`) — so casing fidelity is parser-backend dependent, not a property of `Request.headers`. Iteration itself is not the normalizing step: `multidict.CIMultiDict.items()` does preserve whatever key spelling was stored ("The original casing is preserved. `CIMultiDict` keeps a lower-cased identity internally for lookups."). The rewriting happens earlier, at parse time, in the C parser.

## Source

Primary (mechanism): `aiohttp/_http_parser.pyx` @ v3.14.3 — `find_header()` returns `headers[idx]` (canonical `istr` from the autogenerated `_headers.pxi` tuple) when `_find_header.find_header()` returns an index, and only falls back to `raw_header.decode('utf-8', 'surrogateescape')` when it returns `-1`; `_process_header()` appends that `name` to `self._headers`, and `_on_headers_complete()` builds `headers = CIMultiDictProxy(CIMultiDict(self._headers))` for `RawRequestMessage`.

Primary (why the match is case-insensitive): `tools/gen.py` @ v3.14.3 — `gen_block()` emits `case 'X':` **and** `case 'x':` for every letter of every canonical name in `hdrs.py`, both returning the same `headers.index(term)`.

Corroboration (server wiring): `aiohttp/web_protocol.py` @ v3.14.3 — `RequestHandler.__init__` constructs `HttpRequestParser(...)` imported from `.http`, which re-exports `aiohttp.http_parser.HttpRequestParser`; `http_parser.py` rebinds that name to the Cython class at import time when the extension is available. Internal consistency check: the C parser writes `if not self._lax and name in SINGLETON_HEADERS` (a set of canonical `istr` objects) while the Python parser must write `name.lower() in SINGLETON_HEADERS` — the C form only works because `find_header` already canonicalized `name`.

## Invalidates On

- `aiohttp/hdrs.py` changes (added/removed entries or respelled constants) — regenerates `_headers.pxi` / `_find_header.c` and therefore changes which wire spellings get rewritten.
- The C parser's `find_header()` ceasing to return canonical `istr` objects, or `_process_header()` switching to storing the raw decoded name.
- `tools/gen.py::gen_block` dropping the lowercase `case` emission (making the trie case-sensitive) — then wire casing would survive for known headers too.
- aiohttp upgrading `multidict` past 3.7 in a way that stops `CIMultiDict` keys from retaining their stored spelling.
- The runtime selecting the pure-Python parser (`AIOHTTP_NO_EXTENSIONS=1`, or a build without the C extension) — under that backend the claim **does** hold, so the verdict is backend-conditional and must be re-checked if the deployment target is extension-less.
- Any aiohttp feature that makes casing preservation configurable (e.g. a `preserve_header_case` parser option), which would change the default answer.
