## Claim

Iterating `aiohttp.ClientResponse.headers.items()` yields each header name spelled as the upstream sent it

## What it actually does

`ClientResponse.headers` is the `CIMultiDictProxy` the response parser built (`self._headers = message.headers` in `ClientResponse.start()`), and with the default C/Cython `HttpResponseParser` a header name recognized case-insensitively is stored as aiohttp's **canonical** spelling from `aiohttp/hdrs.py`, not as the upstream sent it: an upstream sending `content-type:` or `CONTENT-TYPE:` yields the key `Content-Type`, `etag`/`ETag` yields `Etag`, `server` yields `Server`, `x-forwarded-for` yields `X-Forwarded-For`. Only names not present in `hdrs.py` — custom `X-…` fields, vendor-specific headers — come back spelled as the upstream sent them. `ClientResponse.raw_headers` is the verbatim `(bytes, bytes)` accessor.

The pure-Python `HeadersParser.parse_headers` does the opposite (`name = bname.decode("utf-8","surrogateescape")`, no case change), so under `AIOHTTP_NO_EXTENSIONS=1` or an extension-less build the claim holds for every header. `multidict.CIMultiDict.items()` is not the normalizing layer — it returns keys with their stored spelling ("The original casing is preserved. `CIMultiDict` keeps a lower-cased identity internally for lookups."); the substitution happens at parse time, before the multidict is built.

⚠ A documentation-only check reads as HOLDS: aiohttp's own "Advanced Client Usage → Response Headers and Cookies" example still shows `resp.headers == {'CONTENT-TYPE': ..., 'SERVER': ..., 'DATE': ...}` and a matching `raw_headers`, which the C parser cannot produce (it would canonicalize those four names). Treat that example as stale; the source above is what is.

## Source

Primary (mechanism): `aiohttp/_http_parser.pyx` @ v3.14.3 — `find_header()` returns `headers[idx]` (the canonical `istr` tuple autogenerated into `_headers.pxi`) whenever `_find_header.find_header()` resolves an index, and only returns `raw_header.decode('utf-8','surrogateescape')` on `-1`; `_process_header()` appends that `name` to `self._headers`; `_on_headers_complete()` builds `headers = CIMultiDictProxy(CIMultiDict(self._headers))` into `RawResponseMessage` for `cparser.HTTP_RESPONSE`.

Primary (why recognition is case-insensitive): `tools/gen.py` @ v3.14.3 — `gen_block()` emits both `case 'X':` and `case 'x':` per letter of every `hdrs.py` name, both returning the same `headers.index(term)`.

Corroboration (client wiring): `aiohttp/client_reqrep.py` @ v3.14.3, line 584 `self._headers = message.headers  # type is CIMultiDictProxy` and line 450 `return self._headers` (the `headers` property) — no re-normalization and no recovery of wire casing anywhere in between.

Contrast (fallback backend): `aiohttp/http_parser.py` @ v3.14.3 — `HeadersParser.parse_headers` stores the raw decoded name, and the module bottom rebinds `HttpResponseParser` to the Cython class when the extension imports.

## Invalidates On

- `aiohttp/hdrs.py` changes — added/removed entries or respelled constants alter which upstream spellings get rewritten (`Etag` vs `ETag` is already a live example of a spelling nobody sends).
- `_http_parser.pyx::find_header` returning the raw decoded name instead of `headers[idx]`, or `_process_header` recording wire casing.
- `tools/gen.py::gen_block` dropping the lowercase `case` emission, making the trie case-sensitive.
- `ClientResponse.start()` switching to sourcing `headers` from `raw_headers` (or aiohttp adding a casing-preserving option), which would make the claim true.
- The runtime selecting the pure-Python parser (`AIOHTTP_NO_EXTENSIONS=1`, or a build without the C extension) — under that backend the claim holds, so this verdict is backend-conditional.
- A `multidict` change that stops `CIMultiDict` keys from retaining the spelling they were added with.
