## Findings

### [P1] Empty-value `Authorization` line deletes a real credential when it arrives first
- **Priority**: P1 — a supplied credential is destroyed on a reachable request, and the base behavior this wave exists to restore did not do this.
- **Location**: `buster_ripper/routes/chat.py:105-121` (`_prepare_headers`), specifically `:113-114` (`token = next((v for v in values if not _is_empty_bearer(v)), None)`) with `buster_ripper/routes/chat.py:124-126` (`_is_empty_bearer`).
- **What is wrong**: `_is_empty_bearer("")` returns `False` — `bool(value)` short-circuits first — so a value-less `Authorization` line counts as a *token* and is selected as the surviving value by the first-match `next()`. When a request carries that blank line **before** a real credential, the loop deletes every `authorization` key from the egress mapping and re-adds `Authorization: ""`. The real credential is gone. The wave's own ledger obligation says the opposite: `DC-S10-C2-r1` requires that "when a credential is present the forwarded request carries that credential". This is the fourth case's remaining hole — F-4 fixed the `"Bearer "`/`"Bearer"` family completely and left the blank-value family half-fixed, in the direction that *loses* data.
- **Evidence (source replay, not reasoning)** — `_prepare_headers` against a `CIMultiDict`, egress values held for the name:

  | inbound values, in wire order | base (`41d3fc6`) | now |
  |---|---|---|
  | `""`, `"Bearer sk-real"` (different spellings) | `["", "Bearer sk-real"]` — credential reaches upstream | `[""]` — **credential deleted** |
  | `""`, `"Bearer sk-real"` (same spelling) | `["Bearer sk-real"]` | `[""]` — **credential deleted** |
  | `"Bearer sk-real"`, `""` (same spelling) | `[""]` | `["Bearer sk-real"]` — improvement |
  | `"Bearer "`, real / real, `"Bearer "` (both orders, both spellings) | collapses per backend | `["Bearer sk-real"]` — the fixed case |

  So the change is a **net regression for two of the four orderings** in this family, and it is order-dependent, which is exactly the property `DC-S10-C2-r1` exists to remove. Reachability was proven by the wave's own technique: `test_duplicate_spellings_never_lose_the_credential` already puts two `Authorization` lines on a raw socket because the aiohttp client collapses them, so a client that sends `-H "authorization:"` twice, or with an unset token variable, is inside this proxy's real input domain (`curl -H "authorization:"` is the ordinary way to produce it).
- **Missing witness**: no test covers a blank value beside a credential. `TestEmptyBearerRule._EMPTY_SPELLINGS` is `("Bearer", "Bearer ")`, the four collapsed-copy pairs all pair a real token with `"Bearer "`, and `test_a_value_less_authorization_line_is_not_touched` asserts only the **lone** blank line (`[("Authorization", "")] → [""]`), which is correct base parity and must keep passing. The parametrized table at `tests/test_header_parity.py:320-329` is the cheapest tier that shows this and is where the case belongs (test-cost rule 3: extend the witness, do not add a module).
- **Reach**: `reached` — raw client socket, one request; no flag, no backend-specific path (both parser backends produce the same wrong egress, because the defect is in the selection, not the collapse).
- **Adversarial-surface citation**: R1 (a decision taken from external input must show its hostile-input set — the set here has a hole at the blank value) and R5 (this is a merge of several values under one name; the near-miss pair `"" ` vs `"Bearer sk-real"` must **not** merge, and today it does, silently, in the losing direction).
- **Fix direction (outcome, not mechanism)**: the surviving value is the one that carries a token; the name is deleted only when no value carries one; and a request whose only value under the name is the blank line keeps forwarding the blank line, per base parity and the existing witness. `062 R-B` still holds: it stays in `_prepare_headers`, on the request's own mapping, with no authorization semantics in `utils.forward_headers`.
