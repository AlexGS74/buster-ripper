## Key Concerns from PASS 1

### 1. Probe-First Duplicates Upstream Requests
The `_probe_for_context_overflow()` function makes a FULL POST request to upstream, then `handle_streaming()` makes ANOTHER full POST request. This:
- Doubles latency for every SGLang streaming request
- Wastes upstream resources (2x inference calls for overflow cases)
- The original issue was "can't retry after headers sent" - but this is solved at a very high cost

**Better approach would have been**: Parse overflow error from the FIRST streaming chunk BEFORE writing to client. The `message_start` event comes early in the stream - could detect overflow there and reset the stream before writing to client.

### 2. Return Type Inconsistency
`handle_streaming()` signature says it returns `web.StreamResponse` but it can now return `web.json_response` (which is `web.Response`). This could cause issues if callers expect StreamResponse methods.

## Findings Analysis

### Architectural Concern: Probe-First Approach Duplicates Requests

**Confidence**: 0.9
**Priority**: P2 (architectural improvement, not blocking)
**Location**: `buster_ripper/routes/messages.py:105-130`
**What's wrong**: The `_probe_for_context_overflow()` function makes a COMPLETE POST request to upstream, then `handle_streaming()` makes ANOTHER complete POST request. For SGLang backends with streaming, this:
- Doubles latency for every request (2 round trips instead of 1)
- Wastes upstream compute (potentially 2 inference calls)
- The original problem "can't retry after headers sent" could be solved more efficiently

**Alternative approach**: Parse the `message_start` event from the first streaming chunk. If it contains an overflow error, close the upstream connection and retry BEFORE writing anything to the client. This would:
- Only make 1 request in the common case (no overflow)
- Still allow retry on overflow
- Not require pre-probing

**Evidence**: Code inspection - `_probe_for_context_overflow` calls `session.post()` with full body
**Pass 1 predicted**: Yes

**However**: This is an ARCHITECTURAL concern, not a correctness bug. The fix DOES solve the original problem correctly - it just does so inefficiently. The tests pass, the behavior is correct, just suboptimal.
